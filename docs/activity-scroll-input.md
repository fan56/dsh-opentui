## 1. Wheel path

- The only live `onMouseScroll` handler is `packages/tui-base/src/component/session-frame.tsx:308-316`. It is on a full-pane overlay box rendered only under `<Show when={activePane() === "right"}>` (`:300-323`). It bounds-checks `sessionScroll.viewport` (`:310-312`), calls `event.stopPropagation()` (`:314`), then `sessionScroll.processMouseEvent(new MouseEvent(sessionScroll, event))` (`:315`).
- `sessionScroll` is a `ScrollBoxRenderable` (`:74`), obtained via `scrollRef` at `:289`; the transcript scrollbox is `packages/tui-base/src/routes/session/transcript.tsx:428-440` (`stickyScroll`/`stickyStart="bottom"`, ref at `:437-439`).
- **No global wheel subscription exists.** `CliRenderEvents` (`@opentui/core/renderer.d.ts:210-228`) has no mouse/scroll enum member (only RESIZE/FRAME/FOCUS/... ). Mouse events are hit-test dispatched to each renderable's `onMouseScroll`/`onMouseEvent` JSX props. `InteractivityProvider` (`packages/tui-base/src/context/interactivity.tsx:6-10`) only gates keymap/input/focus context; it is not a mouse router. So WidgetsDock cannot hook a global wheel stream — it must either own a renderable with `onMouseScroll` or use a nested `<scrollbox>`.
- `@opentui/core` `ScrollBox.d.ts:132-148` (v0.8.1): `scrollByWheel` is **private** (`:134`) and `onMouseEvent` **protected** (`:135`) — the box handles wheel internally; callers cannot invoke a wheel step. Public position API: `scrollTop`/`scrollLeft` get/set (`:75-78`), `scrollHeight`/`scrollWidth` (`:79-80`), `scrollBy` (`:116-119`), `scrollTo` (`:128-131`). `ScrollBoxOptions` (`:12-26`) has scrollX/scrollY/stickyScroll/viewportCulling but **no controlled `scrollTop` option** — set position via the property after `ref`. `defaultFocusable = true` (`:37`) is a focus-singleton hazard next to the composer.
- `MouseEvent` carries the wheel delta directly: `scroll?: ScrollInfo` (`renderer.d.ts:178`), `ScrollInfo = { direction: "up"|"down"|"left"|"right"; delta: number }` (`@opentui/core/lib/parse.mouse.d.ts:1-5`). A manual `onMouseScroll` handler can therefore drive a `cursor` integer with no scrollbox at all.
- In-repo nested-scrollbox precedent: `packages/tui-base/src/routes/session/composer/subagents-tab.tsx:252` (`<scrollbox scrollbarOptions={{visible:false}} maxHeight={5} ref=...>`).
- Can a scrollbox live inside the frame's bordered box? Mechanically the frame is a fixed-height heavy-bordered box (`widgets-dock.tsx:1284-1296`, `height = frameHeight() = 2 + mergedLines().length` at `:1233`). But: (a) D13 requires each line fitted to `width() = dimensions().width - 4` (`:1191`) landing on the right border via `stringWidth` (`merged-dock.ts:9-12,147-173`); a scrollbar gutter would break that unless scrollbar hidden and padding accounted. (b) `defaultFocusable = true` risks stealing composer focus. (c) paint-bug exposure (§5). (d) UNVERIFIED: the session-frame overlay above calls `stopPropagation` only inside the transcript viewport (`:311-315`) — hit-testing when the right pane is active could still swallow lower-zone wheel events; requires tmux verification.

## 4. Cursor state

- WidgetsDock is closure-law: `widgets-dock.tsx:1207-1209` (body declares no reactive state closed over by JSX; header rationale `:34-45`). Module-level-state precedents: `dockSpin` signal (`:322`), `activityFrameLatch` (`:1102`, `createFrameLatch` at `:1063`), `lineFirstSeen` Map (`:278`) reset by `resetSkinLineFades` (`:292-297`).
- Put the lower-zone cursor at module level next to `dockSpin`, e.g. `export const [mergedDockCursor, setMergedDockCursor] = createSignal(0)`, and read it inside `mergedLines()` (`widgets-dock.tsx:1219-1222`) passing `cursor: mergedDockCursor()` into `mergedDockLines` (`MergedDockOptions.cursor` at `merged-dock.ts:82-91`). This survives re-renders and satisfies the closure law.
- **Not safe across sessions without a reset** — same rationale as `lineFirstSeen` (`widgets-dock.tsx:274-276`). Existing reset hook `resetSkinLineFades()` is called at `examples/v2-entry.tsx:856` (reloadSession) and `:923` (session switch). Extend that hook (or add a parallel `resetMergedDockCursor()` called at both sites) so a cursor > 0 from the old session cannot leak. The window builder already clamps out-of-range cursors (`merged-dock.ts:374,380`), which mitigates stale values when content shrinks but is not a substitute for a reset.

## 5. Paint-bug risk

- `docs/upstream-opentui-paint-bug-draft.md:26` (persistent dropped rows under sustained repaint; SIGWINCH does not heal), `:95` (114/125 corrupt frames), `:121-137` (rich per-item/mutating-tail shape → dock damage in 73/78 frames), `:138` — **"Flattened plain-text line window (the scrolled-back rendering path, stable 28-row window): no dock damage at all (0/78 frames) ... a stable flat row window does not collide with the dock."** No workaround short of process restart (`:195`).
- A nested `<scrollbox>` introduces native scroll-state re-layout, optional culling/scrollbar and descendant nodes — closer to the rich shape that damages the dock during a long `await_agent` repaint. The already-implemented manual window (`merged-dock.ts` `assembleZones` at `:368-394`, cursor + `▲/▼` indicators) keeps a fixed flat row list — the shape measured at 0/78 dock damage.
- **Recommendation: B (manual window + wheel/key cursor).** A (nested scrollbox) is the riskiest on paint-bug and focus grounds; C (hybrid) creates two sources of truth (`scrollTop` vs `cursor`). B reuses the existing pure window logic and needs only: an `onMouseScroll` renderable reading `event.scroll.direction/delta`, a module-level cursor, and a gated global key layer.

## 6. Title `N/M`

- Set at `widgets-dock.tsx:1292` `title={mergedTitleText()}`; `mergedTitleText()` (`:1223-1230`) builds the D4 string via `mergedTitle()` (`merged-dock.ts:134-139`), which contains **no** `N/M` today. Append `N/M` in `mergedTitleText()` (or a new pure helper) using the same lower-zone window data the builder uses.
- Spec lines: `docs/activity-merged-widget.md:143` "The title bar shows the lower-zone position `N/M` on its right side."; `:144` "Bottom indicator: `▼ N more`. Top indicator: `▲ N more`."; `:145` "A scroll indicator occupies one line of visible height".
- Unambiguous reading: `N/M` = **lower-zone scroll position** — `N` = ordinal of the first currently visible lower-zone item, `M` = total lower-zone content items (todo rows + agent sub-lines). It is NOT window-start/window-end line numbers, NOT "items shown / total frame lines". Evidence: "position" is singular; indicators count items above/below the window (`topCount = start`, `bottomCount = n - (start+size)` in `merged-dock.ts:386-387`, `n = lowerRaw.length` at `:370`); tests assert `topCount + visibleTodos + bottomCount === total` (`test/merged-dock.test.ts:266-269`). Recommend 1-based `N` for display (spec does not state base — minor ambiguity); compute from the same `start`/`n` used by `assembleZones` so `N/M` and `▲/▼` counts stay consistent.
